# 单元测试实施方案

## 1. 结论与范围

推荐从 **JUnit 5 + kotlin-test + Gradle `test`** 开始，用普通 JVM 测试覆盖不依赖游戏运行状态的 Mod 逻辑。需要注册表、世界、实体、事件生命周期的行为，交给 **Forge GameTest 或实际 Forge 加载验证**；图标、模型和创造模式界面仍需客户端验证。

当前不建议引入 Kotest、MockK、独立测试框架封装或复杂多模块结构。先有真实业务规则和有效断言，再扩展工具。

本次是方案调研与文档交付，不是永久接入测试框架：`build.gradle` 不添加长期测试依赖，`src/test` 不留下探针用例，也不修改生产代码。调研使用临时 Gradle init script 和临时 Kotlin 测试；没有启动 Minecraft 客户端、服务端或 GameTestServer。

## 2. 现状与可测试边界

项目使用 Kotlin 2.2.21、KFF 4.12.0、Forge 1.20.1-47.4.10、Gradle 8.8，Java/Kotlin toolchain 为 17。已有 `test` source set，但 `src/test/kotlin`、`src/test/java`、`src/test/resources` 均为空，构建脚本没有 JUnit 依赖或 `useJUnitPlatform()`。

AI-Factory 框架迁移后，入口为 `com.rcdiamond.aifactory.AIFactory`，Mod ID 为 `ai_factory`。当前只订阅公共初始化事件，没有业务配置、注册内容或客户端专用代码。第 9 节保留此前测试环境调研的历史证据，不是当前框架的游戏加载验证。

此前 `build` 成功并不代表已有单元测试：没有测试源码时，`test` 可以显示 `NO-SOURCE`。

| 当前代码/行为 | 测试边界 | 决策 |
| --- | --- | --- |
| 不访问注册表的字符串、数字和状态计算 | 普通 JVM | 有自定义规则时优先单元测试 |
| `ResourceLocation.tryParse` 的资源 ID 解析 | 可在当前普通测试 JVM 执行 | 适合验证测试环境，不需要长期重复测试 Minecraft 库本身 |
| `AIFactory` | `object` 初始化访问 `MOD_BUS` | 不在普通 JUnit 中初始化入口 |
| `RegistryObject.get()`、方块与物品注册 | 注册生命周期 | Forge 加载或 GameTest |
| 方块放置、破坏和掉落 | 世界与数据包运行状态 | GameTest |
| 创造模式栏内容生成 | 依赖已注册物品及对应事件上下文 | Forge 环境验证；不能靠纯 JVM 断言字段值替代 |
| 模型、纹理、标题与图标显示 | 客户端资源加载和渲染 | 客户端手动验证，必要时独立客户端自动化 |

编译 classpath 上有 Minecraft/Forge，不等于 JVM 已完成 ModLauncher、注册表或 Mod 加载。手工调用 `Bootstrap.bootStrap()` 也不能替代完整 Forge 加载。

## 3. 分层策略

| 层 | 工具/任务 | 主要覆盖 | 默认执行方式 |
| --- | --- | --- | --- |
| 单元测试 | JUnit Jupiter、kotlin-test / `test` | Mod 自身的计算、解析策略、错误处理、状态转换 | 本地与 CI 每次修改执行 |
| 游戏集成测试 | Forge GameTest / `runGameTestServer` | 方块、世界、实体、掉落等实际行为 | 配好测试 source set 后单独执行 |
| 发布与客户端检查 | 构建 JAR、真实 Forge/KFF 环境 | 依赖与类加载、资源显示、UI | 发布前手动检查或专门流程 |

不要把 `runGameTestServer` 挂到默认 `test` 或 `build` 上。普通测试应保持不启动游戏；GameTestServer 本身是游戏服务器进程，并不是另一种 JUnit worker。

## 4. 普通单元测试的接入步骤

### 4.1 添加依赖与测试引擎

将以下内容合并到现有 `build.gradle`，不是替换整个脚本：

```groovy
dependencies {
    testImplementation platform('org.junit:junit-bom:5.11.4')
    testImplementation 'org.jetbrains.kotlin:kotlin-test-junit5:2.2.21'
    testImplementation 'org.junit.jupiter:junit-jupiter'
    testRuntimeOnly 'org.junit.platform:junit-platform-launcher'
}

tasks.withType(Test).configureEach {
    useJUnitPlatform()
    testLogging {
        events 'passed', 'failed', 'skipped'
    }
}
```

- JUnit 5.11.4 是本次验证选择的固定版本，不是“当前最新版”的声明。
- BOM 对齐 Jupiter 与 Platform 版本，避免 API、engine、launcher 不匹配。
- `junit-jupiter` 提供普通用例、参数化用例及 engine；`kotlin-test-junit5` 提供 Kotlin 断言与 JUnit 5 适配。
- `useJUnitPlatform()` 必须配置，否则不能假定 Jupiter 测试会被执行。
- 显式添加 launcher，不依赖 Gradle 临时补齐测试运行库。
- 依赖均为 `testImplementation` / `testRuntimeOnly`，不应进入发布 Mod 的运行依赖。
- 不需要修改现有 Java/Kotlin 17 toolchain，也不要把测试目标改成 Java 21。
- 现有 `sourceSets.configureEach` 已统一 Java、Kotlin 与资源输出；测试输出为 `build/modClasses/test`，不需要再建一套输出目录约定。

### 4.2 目录与 Kotlin 写法

测试使用普通 class，放在 `src/test/kotlin/com/rcdiamond/aifactory/`，测试资源放在 `src/test/resources/`。不要写成需要 KFF 创建的 Mod `object`。

使用 `org.junit.jupiter.api.Test`、`org.junit.jupiter.params.ParameterizedTest` 等注解，断言可使用 `kotlin.test.assertEquals`、`assertNull`、`assertFailsWith`。

以下是调研中使用的环境验证示例，**不是建议长期保留的 Minecraft 库回归测试**：

```kotlin
package com.rcdiamond.aifactory

import net.minecraft.resources.ResourceLocation
import org.junit.jupiter.params.ParameterizedTest
import org.junit.jupiter.params.provider.ValueSource
import kotlin.test.assertNull

class ResourceIdEnvironmentProbe {
    @ParameterizedTest
    @ValueSource(strings = ["AI_FACTORY:machine", "ai_factory:bad space", "a:b:c"])
    fun malformedIdsAreRejected(value: String) {
        assertNull(ResourceLocation.tryParse(value))
    }
}
```

真正的永久测试应调用 Mod 自己的功能入口并验证业务结果，不是复制库实现或固定注册常量。

参数化测试用 `@ValueSource` / `@CsvSource` 处理独立边界；复杂数据使用 `@MethodSource`。若数据工厂放在 Kotlin `companion object` 中，默认静态方法约定需要 `@JvmStatic`，或者明确使用 `@TestInstance(PER_CLASS)` 的实例工厂；不要把所有测试改成共享实例以省略初始化。

Kotlin `internal` 生产成员通常可以由同模块的 `test` 编译访问；这不表示独立 `gameTest` source set 自动拥有相同 friend 配置。不要为覆盖率把私有实现批量改为 public。

### 4.3 运行与报告

完成正式接入并加入真实用例后执行：

```powershell
. .\Set-DevEnv.ps1
.\gradlew.bat test --console=plain
.\gradlew.bat test --tests 'com.rcdiamond.aifactory.SomeBehaviorTest'
.\gradlew.bat check
.\gradlew.bat build
```

`SomeBehaviorTest` 是过滤模式示意，需替换为实际存在的测试类。Gradle 默认将 `test` 接入 `check`，`build` 包含检查阶段，无需另写一个调用 `test` 的包装任务。

报告位置：

- HTML：`build/reports/tests/test/index.html`。
- XML：`build/test-results/test/TEST-*.xml`。

检查是否真的发现并执行了目标用例。`NO-SOURCE`、全部 skipped、错误过滤导致没有匹配用例，不能算测试通过。需要强制重新执行时使用 `test --rerun-tasks`，不要把整仓库 `clean` 当作每次运行测试的前置动作。

在本项目中，执行 `test` 也可能触发 ForgeGradle 的 `jar` / `reobfJar` 依赖任务；这不表示启动了游戏，不应为了减少日志而随意拆掉插件任务依赖。

## 5. 如何增加真正有价值的用例

当前框架只有公共初始化入口，没有独立于 Forge 的业务逻辑。没有必要为了测试数量人为制造“返回 Mod ID”的包装函数。

以后增加机器、配方或物品处理逻辑时，优先把可独立表达的规则保持为小函数或普通类，Forge 适配层只负责取得输入和应用结果。只在实际耦合阻碍测试时做最小分离，不提前搭建通用领域框架。

建议覆盖：

| 规则类别 | 有价值的断言 |
| --- | --- |
| 资源/配置输入策略 | 错误类型、非法格式、不存在的目标与合法输入的区别 |
| 机器处理规则 | 输入不足/刚好足够、输出满、处理失败时资源不被消耗 |
| 数量与能量计算 | 零、阈值两侧、容量限制、溢出处理 |
| 状态转换 | 暂停/恢复、完成只发生一次、取消后没有残留副作用 |
| 配置加载/重载 | 无关配置不改变本 Mod 状态，重载后读取新配置而非旧缓存 |
| 序列化 | 读写往返、无效或缺失字段、版本迁移的业务约定 |

这些是有对应功能时的用例方向，不代表本次新增了机器、能量系统或序列化功能。

未来新增配置时，如果资源 ID 校验策略变复杂，可把不访问注册表的部分分离为独立函数；“ID 已注册”和“解析成实际 Item”的行为仍交给已加载 Forge 的测试。不要在普通 JUnit 中靠重置全局 Forge 注册表来模拟已加载世界。

永久测试应当能捕获使用者可观察的错误。不建议测试：固定默认值、日志文字、源文件内容、注解有没有写、单纯调用转发、mock 返回值再断言相同返回值，以及“没有抛异常”或“集合不为空”这种不说明业务结果的检查。

## 6. Mock、状态隔离与协程

默认不加 MockK/Mockito。优先用真实小对象和确定性输入；只有需要隔离外部 IO、时间或自有接口时才引入替身。

- 替身用于控制环境，不应把整套 Minecraft/Forge API mock 成另一个假游戏。
- 断言业务结果与不变量，而不是只验证某个方法被调用了一次。
- 每个用例独立构造状态，不依赖执行顺序；文件使用 JUnit `@TempDir`，不写实际 `run`、存档或玩家配置。
- 不通过 `Thread.sleep` 等待，避免随机数据、系统时间和外网依赖造成偶发失败。
- 不依赖重置 Kotlin `object` 或反射修改 Forge 私有字段恢复环境。
- 如果业务规则本身使用协程，另加与 KFF 实际协程版本一致的 `kotlinx-coroutines-test`；使用 `runTest` 和虚拟时间测试取消与时序。当前没有协程业务，不需要先加这项依赖。

覆盖率可以在有实质业务测试后用 JaCoCo 增补。先确认所选版本支持相关 JVM/Kotlin 字节码，并核对 Kotlin 生成代码导致的统计偏差；不要以“所有注册字段都被访问过”冒充业务覆盖率，也不先强制整个 Mod 达到一个任意百分比。

## 7. Forge GameTest 的接入条件

本项目已经有 `gameTestServer` 运行配置和 `forge.enabledGameTestNamespaces=ai_factory`，但目前没有 GameTest 用例。现有配置只是启动入口，不能据此声称已经有游戏集成测试。

要真正接入，需完成以下内容：

1. 创建独立的 `src/gameTest/kotlin` 与 `src/gameTest/resources`，并注册 `gameTest` source set。
2. 为该 source set 接入主源码输出和 Forge 编译/运行依赖；保持 Java/Kotlin 17，与现有统一输出约定一致。
3. 只在 `gameTestServer` 的 Mod 源配置中同时纳入主源码与 gameTest 输出，配置独立工作目录，如 `build/gametest-run`。普通客户端、普通服务端与发布 JAR 不纳入测试输出。
4. 用 `@GameTestHolder("ai_factory")` 或 `RegisterGameTestsEvent` 注册测试，测试方法接受 `GameTestHelper`。
5. Kotlin 测试入口需满足 GameTest 的静态方法反射约定，例如 `companion object` 中使用 `@JvmStatic`，不要假设 KFF 对事件 `object` 的支持也会自动处理 GameTest。
6. 提供真实 `.nbt` 结构模板，放在测试资源的 `data/ai_factory/structures/` 中。模板 ID、类名前缀和注解 namespace 必须一致；使用 `@PrefixGameTestTemplate(false)` 时明确模板名称。
7. 完成实际的世界操作后断言结果，并通过 `helper.succeed()`、`succeedWhen` 等方法结束。没有成功状态会超时；异步行为按 tick 调度，不用线程休眠。
8. 在测试源码与模板都准备好后，才执行 `gradlew.bat runGameTestServer`。

这部分是实施步骤，不是已经验证的 source set 配置。GameTestServer 会启动游戏服务器进程，按当前要求本次不执行。没有测试的 GameTestServer 不能当作成功的集成验收。

测试内容优先选真实行为：放置方块后世界状态正确、在约定条件下破坏掉落正确物品、机器处理实际改变库存且失败不消耗输入。不要只验证注册字段能读出来。

GameTest 的必需用例失败会影响服务器退出状态；不要把关键用例标记 `required=false` 来掩盖失败。多个用例可同时在不同场景执行，不应共享坐标、实体或全局可变状态。

GameTest 不覆盖创造模式 UI 的标题、纹理或图标显示，这些仍需客户端检查。发布 JAR 也仍需在真实 Forge/KFF 环境确认类加载，开发 source set 的通过不能替代发布验证。

## 8. 推荐实施顺序与验收

1. 按第 4 节接入 JUnit；新增第一项真实业务规则时，连同有效用例一起提交，避免长期保留一个无测试的“已接入”配置。
2. 针对真实边界增加测试，修 bug 时优先保留能够失败于旧实现、通过于修复后的回归用例。
3. 本地与 CI 运行 `test` / `build`，保留 XML/HTML 报告；测试失败不能忽略。CI 需提供 JDK 17 工具链，并修正项目当前的本机 JDK 21 绝对路径与代理设置。
4. 有世界交互行为需要自动验收时，再落实第 7 节的隔离 GameTest source set 和模板，用单独任务执行。
5. 有足够业务逻辑后再考虑覆盖率或独立纯逻辑子模块；当前单模块无需先拆分。

正式单元测试接入的验收标准：测试 JVM 使用 Java 17；预期用例实际执行；故意破坏被测业务结果时测试能失败；修复后通过；不依赖游戏窗口、用户存档或外网；测试依赖和测试类不进入发布 Mod JAR。

## 9. 本次实测证据与限制

使用临时 Gradle init script 接入第 4 节的 JUnit 依赖，通过当前项目的 `test` 任务执行临时 Kotlin 探针：

```powershell
. .\Set-DevEnv.ps1
.\gradlew.bat -I build/unit-test-probe.init.gradle test --tests probe.UnitTestEnvironmentProbe --console=plain
```

这条命令是调研记录。临时文件在调研结束后删除，不是项目现有的长期入口；正式接入应执行第 4.3 节的命令。

实测结果：

- JUnit 普通用例与参数化用例均被发现、编译和执行，测试 launcher 使用 Java 17。
- 最后一次探针执行为 `BUILD SUCCESSFUL`；XML 报告记录 `tests=6`、`failures=0`、`errors=0`、`skipped=0`。
- 其中 5 个用例验证普通 JVM 能执行资源 ID 解析：完整 namespace、缺省 Minecraft namespace，以及 3 类非法输入。
- 另 1 个诊断用例验证 Forge/KFF 加载上下文不可用。原始测试 classpath 访问 `MOD_BUS` 报 `NoClassDefFoundError: thedarkcolour/kotlinforforge/KotlinModLoadingContext`；仅靠这个错误不能证明完整类路径下的上下文状态。
- 临时显式加入 `testRuntimeOnly 'thedarkcolour:kfflang:4.12.0'` 后再次执行，排除类缺失，访问 `MOD_BUS` 仍报 `NullPointerException: extension(...) must not be null`。因此，“增加加载器 JAR”没有建立真正的 Mod 加载上下文。

最后的诊断用例预期并断言上下文访问失败，所以报告通过；这不是生产 Mod 的加载测试，也没有通过忽略失败来证明 Mod 可用。显式添加 kfflang 仅用于诊断，**不属于第 4 节推荐的纯逻辑单元测试依赖**。

临时 source、init script、测试编译输出和报告均清理，不把 Minecraft 库探针留作永久业务测试。当前生产代码和构建脚本保持不变；GameTest、客户端显示与真正的 Forge 注册行为没有在本次执行。

清理后不使用 init script 再次执行 `gradlew.bat test --console=plain`，结果为 `BUILD SUCCESSFUL`、`test NO-SOURCE`，确认没有把临时探针留在正式测试集中。这个成功只说明原有构建状态恢复，不代表已经永久实施单元测试。
