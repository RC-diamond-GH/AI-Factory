# 开发闭环

所有后续功能、修复与重构遵循：**规划 → 提交 → CI → Code Review → 合并 → CI**。

## 1. 规划

在 issue、PR 或对应设计文档中写清问题、边界、接口、验收方法与风险。先读现有实现和原生依赖合同；多文件改动先明确文件所有权。并行工作使用独立 worktree，约定共享接口，不同时改同一文件。

```powershell
git worktree add -b feat/topic ../AI-Factory-topic main
```

## 2. 提交与 CI

提交一个可解释、可验证的行为切片；不得提交密钥、开发世界、JDK 或构建产物。推送分支并发起指向 `main` 的 PR。CI 为 `.github/workflows/ci.yml`：

- PR、合入 `main` 的 push 和手动触发都会执行。
- Gradle 启动 JVM 为 JDK 21，源码/测试工具链和字节码目标为 JDK 17。
- Linux CI 覆盖仓库中的 Windows 本机 JDK 路径和本机代理，不需要私有 Maven 凭据。
- `build` 执行默认离线业务测试并生成 `jarJar` / `reobfJarJar` 发布包；默认排除 `openai-live`，不读取 `.env`、不调用付费模型 API。
- 检查发布包包含 Kotlin 入口、展开元数据、许可证与 Tokenizer；上传测试报告及不带 `-plain` 的发布 JAR。

```powershell
git push -u origin feat/topic
gh pr create --base main --fill
gh pr checks <PR号> --watch
```

CI 失败必须修正原因并重新提交；不能通过删有意义的测试、隐藏错误或跳过检查来合并。

## 3. Code Review

CI 成功后，审查实际 diff、契约、服务端授权/线程、客户端隔离、资源上限、失败路径、测试和文档。记录审查结论；发现问题就小提交修正，再跑 CI。作者不能用自己的 GitHub 账号批准自己的 PR；独立子代理审查可以作为明确注明来源的 PR 评论记录，但不得冒充另一个人的 GitHub approval。

合并前检查 PR 的**最新 head commit**，而不是旧提交上的绿灯。若审查之后代码变化，需要重新审查变化部分。

## 4. 合并与主分支 CI

```powershell
gh pr merge <PR号> --squash
gh run list --branch main --workflow ci.yml --limit 5
gh run watch <run-id> --exit-status
```

PR CI 检查拟合并代码，主分支 CI 检查真实合并结果，两者不可互相替代。必须等主分支检查结束，再将切片标记为完成。

## 5. 权限与证据边界

推荐为 `main` 配置必须通过 `Build and package (Java 17)`、必须走 PR、禁止 force push 的分支保护；是否能强制执行取决于 GitHub 仓库套餐和权限。流程文档不是已经启用分支保护的证明。只有实际设置成功才可宣称已强制。

构建及 JAR 检查不代表 Minecraft 加载、UI、多人或真实变量卡求值已经通过。按本仓库约定，自动化不启动客户端/服务端、不代用户接受 EULA；交付必须区分实际烟测与留给使用者的游戏内验收。
